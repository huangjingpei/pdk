# PDK 商业化平台 · 客户端接入方案（含 Python SDK）

> 本文基于**后端真实 API**（逐文件核对 `ClientAuthController` / `ClientDeviceLicenseController` /
> `ClientAccountController` / `DeviceLicenseService` / `DeviceSecurityInterceptor` /
> `ClientCryptoAdvice` / `BodyCryptoService`），描述的是**当前生效**的协议。
> 旧的 `CLIENT_INTEGRATION_GUIDE.md`（AES-128-GCM + 字节翻转 + 静态盐方案）已废弃，请勿混用。

适用对象：桌面客户端 / 机器人脚本 / 第三方集成。本文以「两个客户端分别接入 `ZHIBO_AI`(appId=2) 与
`ZHIBO_LIVE`(appId=3)」为例，但方案对全部业务通用。

## 1. 后端全部业务清单

种子数据（`schema-mysql.sql`）当前共 3 个业务，两种授权模型：

| appId | bizCode | 名称 | 授权模型 | 注册方式 | 状态 | 客户端接入要点 |
|---|---|---|---|---|---|---|
| 1 | `PDD` | 拼多多业务 | `USER_SUBSCRIPTION` | `SELF_SERVICE`（可自助注册） | ACTIVE | 账号订阅：登录即绑设备，靠次数/套餐到期；卡密核销走 `/api/v1/card/activate` |
| 2 | `ZHIBO_AI` | 直播 AI | `DEVICE_LICENSE` | `ADMIN_ONLY`（后台建账号） | DISABLED→需启用 | 设备许可证：一张卡密=一台机器，按到期计费、次数无限 |
| 3 | `ZHIBO_LIVE` | 直播矩阵 | `DEVICE_LICENSE` | `ADMIN_ONLY`（后台建账号） | DISABLED→需启用 | 同上，并额外提供推流票据接口 |

> 你的两个客户端（`zhibo_ai` / `zhibo_live`）本质是**同一套客户端程序，仅 `app_id` 配置不同**
> （2 和 3）。它们都走 `DEVICE_LICENSE` 模型。

## 2. 鉴权与会话模型

- 业务通过请求头 **`X-PDK-App-ID`** 指定（值为 appId 整数）。
- 登录态由 **Sa-Token** 维护，存在两个独立的 loginType：`admin`（后台）与 `client`（客户端）。
  客户端用 `clientStpLogic`，登录后返回一个令牌。
- 登录响应里**直接返回令牌的键名和值**：
  ```json
  { "tokenName": "satoken", "tokenValue": "eyJ...", ... }
  ```
  客户端应读取 `tokenName` 作为请求头名、`tokenValue` 作为值，后续请求带上。
- **`DEVICE_LICENSE` 的令牌主体是 `license:<许可证ID>`**，不是用户 ID。所以换设备 / 许可证作废后，旧令牌直接失效，必须重新登录（带卡密）。
- **`USER_SUBSCRIPTION` 的令牌主体是用户 ID。**

### 每个受保护请求必带的安全请求头

| 请求头 | 取值 | 说明 |
|---|---|---|
| `X-PDK-App-ID` | 业务 appId | 业务路由 |
| `X-PDK-Phone` | 登录手机号 | 与令牌会话一致性校验（不一致 → 40102） |
| `X-PDK-Device-ID` | 稳定机器指纹 | 设备绑定 / 单设备互踢校验 |
| `<tokenName>` | `tokenValue` | Sa-Token 会话令牌 |

> 公开接口（无需上述令牌）：`/api/v1/client/config/public`、
> `/api/v1/client/business/by-app/{appId}`、`/api/v1/client/auth/*`（登录/注册/短信/改密/重置）。

## 3. 客户端标准操作流程

### 3.1 登录 + 设备激活（DEVICE_LICENSE）

`POST /api/v1/client/auth/login`

```json
{
  "appId": 2,
  "phone": "13454118763",
  "password": "客户端密码(SHA无关，明文传输由通道/加密层保护)",
  "deviceId": "稳定机器指纹",
  "deviceName": "张老板的机器A",
  "platform": "windows",
  "clientVersion": "1.0.0",
  "cardKey": "PDK-XXXX-XXXX-XXXX"   // 仅「新设备首次绑定」需要
}
```

服务端 `DeviceLicenseService.authenticateAndBind` 逻辑（即「激活设备」）：
- 本设备已绑定过该许可证 → 直接复用，返回现有许可证。
- 本设备未绑定且**带了 `cardKey`** → 校验卡密归属当前手机号、未被他人设备占用，绑定设备并**在首次激活时开始计算到期时间**（`expireAt = 激活时刻 + 套餐时长`）。
- 本设备未绑定且**没带 `cardKey`** → 抛 `40380`「当前电脑尚未绑定许可证，请输入分配给您的卡密」。

所以：**「激活设备」= 在新机器上带卡密登录一次**。已激活的机器日常登录可省略 `cardKey`。

响应（节选）：
```json
{
  "code": 200,
  "data": {
    "tokenName": "satoken",
    "tokenValue": "eyJ...",
    "phone": "13454118763",
    "authorizationMode": "DEVICE_LICENSE",
    "deviceLicense": { "licenseId": 12, "status": "ACTIVE", "expireAt": "2026-09-30T12:00:00",
                       "remainingCalls": 2147483647, "packageName": "ZHIBO_AI-月卡" }
  }
}
```

### 3.2 修改密码（记得旧密码）

`POST /api/v1/client/auth/change-password` → `{appId, phone, oldPassword, newPassword}`
成功后**强制踢掉该用户全部在线会话**（含其所有许可证），需重新登录。

### 3.3 找回密码（忘记密码，短信验证码）

1. `POST /api/v1/client/auth/sms/send` → `{appId, phone, purpose: "RESET_PASSWORD"}`
   返回 `expireMinutes: 5`（及调试模式下可能返回 `debugCode`）。
2. `POST /api/v1/client/auth/reset-password` → `{appId, phone, smsCode, newPassword}`
   成功后同样踢掉全部旧会话。

### 3.4 解绑设备 / 注销

- `POST /api/v1/client/auth/unbind-device`
  - `DEVICE_LICENSE`：解绑当前许可证绑定的设备，**有效期继续计算**，客户可在新电脑用原卡密重新登录。
  - 账号订阅：解绑用户设备并注销会话，可在新电脑重登。
- `POST /api/v1/client/auth/logout`：注销当前会话。

### 3.5 许可证与套餐查询

| 方法 & 路径 | 说明 |
|---|---|
| `GET /api/v1/client/device-license/current` | 当前设备许可证详情 |
| `GET /api/v1/client/device-license/devices` | 该用户在本业务下全部许可证 |
| `GET /api/v1/client/device-license/renewal-history` | 续费历史 |
| `GET /api/v1/client/account/profile` | 账户 + 许可证快照（含 `expireTime`/`status`） |
| `GET /api/v1/client/account/usage` | 用量与调用记录 |
| `GET /api/v1/client/account/card` | 当前卡密 / 套餐 / 资源 |

### 3.6 ZHIBO_LIVE 推流票据（业务专属扩展）

`ZHIBO_LIVE` 客户端在拿到许可证后，可进一步申请推流票据：
- `POST /api/v1/client/zhibo-live/publish-tickets` → 签发推流票据（连接 MediaMTX 用）
- `GET  /api/v1/client/zhibo-live/streams/current` → 当前推流会话
- `POST /api/v1/client/zhibo-live/streams/{sessionNo}/stop` → 停止推流

### 3.7 USER_SUBSCRIPTION（PDD）补充链路

- 卡密核销：`POST /api/v1/card/activate`（`ActivateCardDTO`：卡密 `PDK-xxxx-xxxx-xxxx`、手机号、设备ID）。
- 资源调度：`POST /api/v1/dispatch/acquire-token`（申请短效加密资源 Token）、
  `POST /api/v1/dispatch/report-result`（异步上报结果并扣次/自愈）。
- 这两个接口同样受 `DeviceSecurityInterceptor` 保护（需上文 4 个安全头）。

## 4. 不做心跳的「合法检查」机制（核心）

客户端**不需要**周期性心跳。合法性由服务端在**每一个受保护请求**上强制校验 ——
`DeviceSecurityInterceptor.preHandle` 依次做：

1. 由 `X-PDK-App-ID` 解析业务上下文。
2. `clientStpLogic.checkLogin()`：令牌必须有效。
3. 必须携带 `X-PDK-Phone` 与 `X-PDK-Device-ID`，否则 `40101`。
4. **DEVICE_LICENSE**：调用 `deviceLicenseService.requireSubject(...)`：
   - 令牌主体须为 `license:<id>`，且许可证属于当前业务；
   - 绑定设备须为 `ACTIVE` 且与请求 `X-PDK-Device-ID` 一致（否则 `40103` 设备踢出）；
   - 自动 `refreshExpired`：到期时间已过则标记为 `EXPIRED`；
   - 对「需要付费许可证」的接口（除 profile/card/usage/device-license/*/unbind/logout/devices 外），
     进一步 `requireActive`：必须 `ACTIVE` 且未到期，否则：
     - `40381` 许可证已到期
     - `40384` 许可证已暂停/作废
     - `40374` 可用次数不足（账号订阅路径）
5. **USER_SUBSCRIPTION**：用户存在且未冻结、业务匹配、手机号一致、单设备互踢（`40103`）。

### 客户端如何「自查」而无需心跳

在每次业务操作前，先调一次 `GET /api/v1/client/account/profile`，解析返回判断：

- `authorizationMode == "DEVICE_LICENSE"`：看 `deviceLicense.status` 与 `deviceLicense.expireAt`；
  `expireAt` 已过或 `status != ACTIVE` → 提示「许可证已到期/已暂停，请续费或联系管理员」。
- 任何受保护请求若返回以下错误码，按策略处理：

| 错误码 | 含义 | 客户端应对 |
|---|---|---|
| `40101` | 缺安全请求头 | 补全 `X-PDK-Phone` / `X-PDK-Device-ID` |
| `40102` | 会话与手机号不一致 | 重新登录 |
| `40103` | 设备被踢（账号已在其他电脑登录） | 提示用户、引导重新登录 |
| `40106` | 会话不属于当前业务 / 非设备许可证会话 | 用正确 appId 重新登录 |
| `40380` | 本设备未绑定许可证 | 带 `cardKey` 重新登录（激活设备） |
| `40381` | 许可证已到期 | 引导续费 |
| `40382` | 卡密不存在/未分配/已作废 | 联系管理员核对卡密 |
| `40383` | 卡密已绑其他设备 | 原设备解绑或后台解绑后再绑 |
| `40384` | 许可证已暂停/作废 | 联系管理员 |
| `40385` | 当前设备没有许可证 | 分配并激活 |
| `40980/40981` | 设备/卡密并发冲突 | 短暂退避后重试 |
| `42900~42905` | 加密相关（强制加密/密钥版本/重放/解密失败） | 见第 5 节 |

> 结论：**服务端是「合法检查」的唯一裁判**，客户端只负责把 4 个安全头带齐、把令牌带对，
> 并在拿到 `40xxx` 时做友好提示与重新登录。不要缓存「是否合法」的结论超过一次操作。

## 5. 通信加密（信封）规范

默认 `security.encryption.mode = optional`：**客户端可明可密**。若设为 `force` 则必须加密（否则 `42900`）。
加密仅作用于 `/api/v1/client`、`/api/v1/dispatch`、`/api/v1/card` 下的接口。

信封结构（请求与响应同构）：

```json
{
  "kid":  "v1",                         // 密钥版本，与公钥一一对应（来自 /config/public）
  "enc":  "base64( RSA-OAEP(SHA-256+MGF1)(32字节AES密钥) )",
  "iv":   "base64( 12字节 GCM nonce )",
  "data": "base64( AES-256-GCM 密文 + 16字节认证标签 )",
  "ts":   1700000000000,               // 毫秒时间戳，±5 分钟防重放
  "rnd":  "随机串，防重放"
}
```

要点：
- **请求**：客户端用**服务端公钥**（RSA-OAEP SHA-256/MGF1）包装一次性 AES-256 密钥，AES-GCM 加密 body。
- **响应**：服务端用**同一把 AES 会话密钥**加密返回（不再做 RSA），客户端用同一密钥 + 响应里的 `iv` 解密。
- GET（无 body）通常返回明文；若近期发过加密 POST，服务端会用按 `appId+deviceId` 缓存的会话密钥加密 GET 响应（30 分钟 TTL）。
- 公钥获取：`GET /api/v1/client/config/public` → `{ encryptionMode, publicKey(PEM), kid, supportedKids, publicKeyFingerprint }`。

> 最低可用方案：**全程明文**（依赖 HTTPS 传输层保护）。需要更强保护时再开启信封加密。
> Python 实现见 `client/python/pdk_client.py`（`use_crypto=True`）。

## 6. Python SDK 使用

SDK 文件：`client/python/pdk_client.py`（依赖 `requests`、`cryptography`）。
它已封装：4 个安全头、令牌保存、登录/激活/改密/找回/解绑、许可证查询、`verify_session()` 合法自查、可选信封加密。

### 6.1 两个客户端的配置示例

```python
from pdk_client import PdkClient

# zhibo_ai 客户端
ai = PdkClient("http://localhost:8080", app_id=2, phone="13454118763",
               device_id="稳定机器指纹-AI")
ai.login(password="ClientPass123", card_key="PDK-1234-5678-90AB")  # 新设备带卡密=激活
print(ai.verify_session())   # 无心跳自查

# zhibo_live 客户端（同一份程序，仅 app_id 不同）
live = PdkClient("http://localhost:8080", app_id=3, phone="13454118763",
                 device_id="稳定机器指纹-LIVE")
live.login(password="ClientPass123", card_key="PDK-2222-3333-4444")
```

### 6.2 业务操作前做合法自查（推荐模式）

```python
def safe_op(client: PdkClient, do_work):
    st = client.verify_session()
    if st.get("expired"):
        raise RuntimeError("许可证已到期，请续费")
    if st.get("license_status") not in (None, "ACTIVE"):
        raise RuntimeError(f"许可证状态异常: {st.get('license_status')}")
    return do_work()   # 真正干活（如申请推流票据 / 调用业务 Handler）
```

### 6.3 找回密码流程

```python
c = PdkClient("http://localhost:8080", app_id=2, phone="13454118763")
c.send_sms(purpose="RESET_PASSWORD")          # 取短信码（调试环境可能返回 debugCode）
c.reset_password(sms_code="123456", new_password="NewPass123")
# 成功后旧会话被踢，用新密码重新 login
```

## 7. 常见坑

1. **两个业务 = 两个独立用户行**：`(bizId, phone)` 唯一。同一手机号开 ZHIBO_AI 与 ZHIBO_LIVE，
   是两个用户、两套许可证、两套令牌，不可混用 —— 各自用对应 `app_id` 登录。
2. **deviceId 必须稳定**：它是设备绑定的依据。每次启动都变会导致频繁 `40103` 互踢或反复要求激活。
   建议用主板序列号 / MAC 哈希做稳定指纹。
3. **DEVICE_LICENSE 令牌主体是 `license:<id>`**：换机器 / 作废 / 过期后旧令牌直接失效，别缓存令牌长期用，
   遇到 `40106`/`40381` 就重新登录。
4. **到期时间从「首次激活」起算**：管理员分配后显示「未激活·暂不计时」是正常的；客户首次用卡密登录才计时。
5. **卡密格式**：`PDK-XXXX-XXXX-XXXX`（大写+连字符），激活时校验正则。
6. **加密模式默认 optional**：不实现信封也能跑；一旦服务端切到 `force`，所有 `/client`、`/dispatch`、`/card`
   请求必须走信封，否则 `42900`。
7. **公开接口不受拦截器保护**：`/config/public`、`/business/by-app/{id}`、`/auth/*` 不需要令牌，
   但业务类接口（`/account/*`、`/device-license/*`、`/zhibo-live/*`、`/dispatch/*`）必须 4 头 + 令牌。

| 区间 | 含义 |
|---|---|
| `400xx` | 参数/业务前置错误（appId 缺失 40050、套餐停用 40020、手机号已注册 40010、新密码同旧 40019、非设备许可证模式 40058） |

## 9. 设备指纹与「防克隆」检测（不做心跳）

针对 `DEVICE_LICENSE` 业务（ZHIBO_AI / ZHIBO_LIVE）。目标是把「复制注册表 / 整盘克隆」的攻击成本抬高到
需要 root/逆向才能绕过，并在异常时**可感知、可裁决**——客户端方案永远可被有 root 权限的人绕过，
所以关键在服务端能否发现异常。

### 9.1 客户端要做什么
1. **稳定 deviceId + 注册表持久化**：Windows 写入 `HKCU\Software\PDK\<appId>\Device` 的 `DeviceId`（UUID），
   重装/重启不丢；非 Windows 回退到用户主目录文件（见 `client/python/pdk_client.py` 的 `_load_or_create_device_id`）。
   注册表解决了 deviceId 的「稳定性」，但要防克隆还必须配合服务端指纹比对。
2. **采集硬件指纹**：仅主板序列号 / 磁盘序列号 / CPUID（Windows 通过 PowerShell/WMI `collect_fingerprint()`）。
   任一为空/默认值（云/VM 常返回 `To be filled by O.E.M.`、`Default string` 等）视为不可读，**不计入置信度**。
3. **上报与回传**：
   - 登录 `POST /client/auth/login` 的 body 带 `fingerprint:{motherboardSerial,diskSerial,cpuid}`（明文；
     服务端做 **salted hash**，绝不落库明文）。
   - 登录响应下发 `fingerprintHash`（服务端对原始组件做 salted hash 的结果）；
     客户端缓存它，**之后每次受保护请求自动带 `X-PDK-FP: <fingerprintHash>` 头**。
   - 服务端在 `DeviceSecurityInterceptor` → `requireSubject` 中**每次请求**比对 `X-PDK-FP` 与库内哈希，
     实现「不做心跳的克隆/换机检测」：不匹配即 `40103` 会话失效，需重新登录。

### 9.2 服务端三层防御
| 层 | 触发 | 处理 |
|---|---|---|
| ① 注册表持久 UUID（令牌） | 主身份 | 稳定、防误丢；**不防克隆**（可导出导入） |
| ② 设备内指纹剧变 | 同一令牌下指纹相似度 `< 0.5` | 抛 `40386` 疑似克隆；`0.5~0.85` 标记 `CLONE_SUSPECT` 但放行并告警 |
| ③ 跨设备指纹碰撞 | 同业务内相同 `fp_hash` 被**不同设备令牌**声明 | 抛 `40386` 疑似克隆 |

### 9.3 极端情况：硬件指纹仍可能不唯一 → 预防策略
- **退化指纹保护**：三个组件全空/默认值 → `fp_confidence=0`、`fp_hash=NULL` → **不做指纹克隆判定**，
  仅以 deviceId 令牌为主键，避免「所有人指纹全相同」导致的误杀/误放行。
- **跨设备碰撞仅在 `confidence>=2`（至少两个组件可读）时启用**，规避单组件弱指纹偶发碰撞误杀合法用户。
- **deviceId 令牌始终是绑定主轴**，指纹只是辅助信号：克隆判定只「暂停/存疑」，不会让拥有唯一令牌的合法用户被错杀。
- 原始表 `pdk_user_device` **未改动**；指纹独立成 `pdk_device_fingerprint` 表（1:1，`user_device_id` 唯一，
  索引 `idx_biz_fphash(biz_id,fp_hash)`），`spring.sql.init` 会在重启时自动建表（无需手工迁移）。
