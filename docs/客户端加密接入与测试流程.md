# 客户端加密接入与服务端交互全流程

> 面向**客户端开发者**：讲清楚「客户端 SDK 与服务端之间，加密到底怎么跑、怎么测、哪里最容易踩坑」。
> 算法与字段以**后端实际代码**为准（`BodyCryptoService` / `ClientCryptoAdvice` / `SecurityKeyService`），
> 与设计文档 `docs/protocol-encryption-design.md` 有出入的地方已在文末「差异说明」标注。
>
> 状态：加解密链路已于 2026-08-31 通过真实后端端到端验证（`client/python/simulate_crypto.py` 10/10 PASS）。

---

## 0. 一句话概览

在 HTTPS 之上再叠一层**应用层报文加密**：客户端每次请求随机生成一把 AES-256 密钥 `K`，用**服务端公钥**做
RSA-OAEP 包装后随报文一起发；服务端私钥解出 `K`，用 `K` 解密 body，**并复用同一把 `K` 加密响应**。
客户端本地持有 `K`，直接对称解密响应——响应侧零 RSA 开销。

**只加密 HTTP body，不加密 URL / query / header。**

---

## 1. 完整交互链路（8 步）

| # | 方 | 动作 | 关键细节 |
|---|---|---|---|
| ① | 客户端 | `GET /api/v1/client/config/public` | 免鉴权。拿公钥 PEM、`kid`、加密 `mode`、指纹 |
| ② | 服务端 | 返回配置 | `{encryptionMode, publicKey, kid, supportedKids, publicKeyFingerprint}` |
| ③ | 客户端 | 构造信封（本地，无网络） | 随机 `K`(32B) → AES-256-GCM 加密 body；RSA-OAEP(公钥) 包装 `K` |
| ④ | 客户端 | 用信封 JSON **整体替换** body 发出 | `POST /api/v1/client/auth/login` |
| ⑤ | 服务端 | 按 `kid` 取私钥解出 `K` → AES-GCM 解密 body | 得到原始业务 JSON |
| ⑥ | 服务端 | 防重放校验 | `ts` 在 ±5 分钟内；`rnd` 不可重复 |
| ⑦ | 服务端 | 业务处理 → 用**同一把 `K`** 加密响应 | 不再做 RSA |
| ⑧ | 客户端 | 用本地 `K` 解密响应 | 得到 `CommonResult` |

关键点：**`K` 是一次性的、每请求随机生成**，但**一次请求-响应往返内复用**。

## 2. 阶段一：引导（拉公钥 + 指纹钉扎）

### 2.1 请求

```http
GET /api/v1/client/config/public HTTP/1.1
X-PDK-App-ID: 3
```

免鉴权、免设备拦截器，且**本身不加密**（否则客户端无法引导启动）。

### 2.2 响应

```json
{
  "encryptionMode": "optional",
  "publicKey": "-----BEGIN PUBLIC KEY-----\nMIIBIjANBg...\n-----END PUBLIC KEY-----",
  "kid": "v1",
  "supportedKids": ["v1"],
  "publicKeyFingerprint": "a1b2c3d4e5f6..."
}
```

| 字段 | 用途 |
|---|---|
| `encryptionMode` | `off` / `optional` / `force`，决定客户端是否启用加密 |
| `publicKey` | 服务端 RSA-2048 公钥 PEM，用于包装会话密钥 |
| `kid` | 当前激活密钥版本，信封里要原样带回 |
| `supportedKids` | 服务端当前接受的全部版本（轮换期会有多个） |
| `publicKeyFingerprint` | `SHA-256(DER(SubjectPublicKeyInfo))` 前 16 字节 = 32 位 hex |

### 2.3 指纹钉扎（防假公钥 MITM，生产必做）

三层优先级：

1. **显式 pin**：构造客户端时传入预置指纹，与端点返回不一致 → 立即拒绝握手。
2. **本地 pin-store（TOFU）**：未显式 pin 时读写 `~/.pdk_client/pin.json`，首次成功连接即信任并落盘，之后每次比对。
3. **未配置**：跳过校验（仅开发期）。

> `client/python/pdk_client.py`（测试用轻量客户端）**未实现钉扎**，生产请用 `sdk/python` 的 `PdkApiClient`。

## 3. 阶段二：请求加密（构造信封）

### 3.1 信封格式

原始业务 JSON 被**整体加密**后，body 替换为：

```json
{
  "kid": "v1",
  "enc": "Base64( RSA-OAEP(服务端公钥, 32字节随机密钥 K) )",
  "iv":  "Base64( 12字节随机 GCM nonce )",
  "data":"Base64( AES-256-GCM(K, iv, 明文JSON) ‖ 16字节认证标签 )",
  "ts":  1730000000000,
  "rnd": "随机字符串"
}
```

| 字段 | 说明 |
|---|---|
| `kid` | 选哪个公钥加密的，服务端据此路由私钥 |
| `enc` | 被包装的会话密钥。`data` 的密文**不含** K |
| `iv` | 12 字节随机值，每次请求必须重新生成 |
| `data` | 密文 **+ 尾部 16 字节 GCM tag**（见 §6.3，跨语言实现最容易错的地方） |
| `ts` | 毫秒时间戳，防重放窗口 ±5 分钟 |
| `rnd` | 随机串，服务端按 `pdk:replay:<rnd>` 去重 |

### 3.2 算法参数（**必须严格对齐，否则必失败**）

| 项 | 值 |
|---|---|
| 非对称 | `RSA-2048`，`RSA/ECB/OAEPWithSHA-256AndMGF1Padding` |
| **OAEP 主哈希** | SHA-256 |
| **MGF1 哈希** | **SHA-256**（⚠ 见 §6.1，本轮真实 Bug） |
| 对称 | `AES-256-GCM`，12 字节 IV，128 bit tag |
| 时间戳 | 毫秒，±5 分钟 |

### 3.3 参考实现（Python，`pdk_client.py:234`）

```python
def _encrypt_body(self, plain_str: str) -> str:
    pub = self._load_pub_key()
    aes_key = AESGCM.generate_key(bit_length=256)   # 32 字节，每次请求随机
    iv = os.urandom(12)                              # 12 字节 GCM nonce
    ct = AESGCM(aes_key).encrypt(iv, plain_str.encode("utf-8"), None)
    enc = pub.encrypt(
        aes_key,
        asym_padding.OAEP(
            mgf=asym_padding.MGF1(hashes.SHA256()),  # ⚠ MGF1 必须显式 SHA-256
            algorithm=hashes.SHA256(),
            label=None,
        ),
    )
    envelope = {
        "kid": self._kid,
        "enc": base64.b64encode(enc).decode("ascii"),
        "iv":  base64.b64encode(iv).decode("ascii"),
        "data": base64.b64encode(ct).decode("ascii"),
        "ts": int(time.time() * 1000),
        "rnd": "".join(random.choices(string.ascii_letters + string.digits, k=16)),
    }
    self._session_key = aes_key      # 服务端会用同一把 K 加密响应
    return json.dumps(envelope, ensure_ascii=False)
```

### 3.4 抓包前后对比

**明文（旧客户端，抓包可见账号密码）**

```http
POST /api/v1/client/auth/login HTTP/1.1
Content-Type: application/json

{"phone":"13800000000","password":"...","deviceId":"XPLAIN-..."}
```

**加密后（抓包只见信封）**

```http
POST /api/v1/client/auth/login HTTP/1.1
Content-Type: application/json

{"kid":"v1","enc":"j9k2...","iv":"8f3A...","data":"Hk7p...","ts":1730000000000,"rnd":"Qz4x..."}
```

请求行、header 仍明文，但 body 里的手机号/密码/设备 ID 已是密文——
**攻击者能知道"你在登录"，但拿不到账号密码。**

## 4. 加密边界：到底加密了什么

| HTTP 组成 | 是否加密 | 说明 |
|---|---|---|
| 请求行（`POST /path HTTP/1.1`） | ❌ | 加密会破坏路由 |
| **Query string**（`?page=1`） | ❌ | ⚠ **敏感参数不要放 query** |
| **HTTP headers** | ❌ | `satoken`、`X-PDK-Phone`、`X-PDK-Device-ID` 全部明文 |
| **请求 body** | ✅ | 整段业务 JSON 被信封替换 |
| 响应状态行 / headers | ❌ | |
| **响应 body** | ✅ | 仅当已建立加密会话 |

这是**有意取舍**：加密 URL/header 会破坏 HTTP 路由、CDN、网关与负载均衡。
真正承载业务机密的是 body。**若 header/query 里有敏感信息，应移到 body 里传。**

### 4.1 生效路径

后端 `ClientCryptoAdvice.isProtectedPath` 判定（以代码为准）：

- `/api/v1/client/**`
- `/api/v1/dispatch/**`
- `/api/v1/card/**`

**不生效**：`/api/v1/admin/**`、`/actuator/**`、`/api/v1/client/config/public`（引导端点本身）。

### 4.2 multipart 上传不在范围内

`multipart/form-data` 走二进制流通道，不经 `@RequestBody` 文本解析。
如需对上传内容保密，**由业务层先加密文件字节再上传**。

## 5. 阶段三：服务端处理

### 5.1 解密流程（`BodyCryptoService.decryptEnvelope`）

1. 按信封 `kid` 查私钥 → 查不到抛 **42901**。
2. RSA-OAEP 解出 32 字节 `K`。
3. AES-256-GCM 解密 `data` → 得到明文业务 JSON（GCM 自带完整性校验，**任何篡改都会失败**）。
4. 防重放：`|now - ts| > 5min` → **42902**；`rnd` 重复 → **42903**。
5. 全部异常兜底 → **42904**（解密失败）。

### 5.2 三态模式（`security.encryption.mode`）

| 模式 | 收到信封 | 收到明文 | 用途 |
|---|---|---|---|
| `off` | 按明文透传（不解密） | 透传 | 紧急关闭 |
| `optional` | 解密 | **透传放行** | **默认**，灰度期新旧客户端并存 |
| `force` | 解密 | **拒绝 42900** | 全量验证后切换 |

### 5.3 响应加密判定（重点：GET 也能加密）

服务端用两条路径决定「响应要不要加密」：

- **本次请求是信封** → 用本次的 `K` 加密响应（ThreadLocal，同线程必然成功）。
- **无 body 的 GET** → 查**跨请求会话密钥缓存** `SESSION_KEYS`：
  前端任一加密 POST（如登录）成功后，服务端把 `K` 按
  **`appId` + `X-PDK-Device-ID`** 存入缓存（TTL 30 分钟）；
  之后该身份在受保护路径上的 GET 响应统一用这把 `K` 加密。

| 接口类型 | 请求 | 响应 |
|---|---|---|
| POST/PUT（带 body） | 加密 ✅ | 加密 ✅ |
| GET（已建立加密会话） | 明文（无 body） | **加密 ✅** |
| GET（尚未建立加密会话） | 明文 | 明文（灰度降级） |

> ⚠ **对客户端的硬要求：每次请求都必须携带稳定的 `X-PDK-Device-ID`。**
> 服务端靠它识别会话身份。deviceId 一变，缓存就查不中，GET 响应会静默降级为明文。

### 5.4 响应信封的 `enc` 是空串

响应**复用请求的会话密钥**，客户端本地已有 `K`，不需要也不能再做 RSA。
因此响应信封的 `enc` 字段恒为空字符串 `""`：

```json
{"kid":"v1","enc":"","iv":"RvLCAsu7Iwy2rZwe","data":"qG0GunJi+...","ts":...,"rnd":"..."}
```

**客户端解密时请忽略 `enc`，直接用缓存的 `K` 解密 `data`。**
（早期实现曾把明文会话密钥塞进 `enc`，属密钥泄露，已修复。）

## 6. 跨语言避坑清单（本轮修复的 3 个真实 Bug）

这一节是实测中真正卡住的地方，**新写客户端 SDK 必读**。

### 6.1 ⚠ Java OAEP 的 MGF1 默认是 SHA-1（→ 42904）

**现象**：Python / C++ 客户端加密登录恒返回 `42904 报文解密失败`，Java 客户端自测却正常。

**根因**：Java 的 `Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding")`
在**不显式传参**时，MGF1 默认用 **SHA-1**（只有主哈希是 SHA-256）。
而 Python(cryptography)、C++(OpenSSL `EVP_sha256`)、Go、.NET 的 OAEP-SHA256 **默认 MGF1 也是 SHA-256**。
两侧 MGF1 不一致 → RSA 解密失败。

**服务端已修**（`BodyCryptoService`）：

```java
private static final OAEPParameterSpec PDK_OAEP_PARAMS =
        new OAEPParameterSpec("SHA-256", "MGF1", new MGF1ParameterSpec("SHA-256"),
                PSource.PSpecified.DEFAULT);
rsa.init(Cipher.DECRYPT_MODE, priv, PDK_OAEP_PARAMS);   // 必须显式传参
```

> Java 包路径不对称，别踩：`OAEPParameterSpec` / `PSource` 在 `javax.crypto.spec`，
> 但 **`MGF1ParameterSpec` 在 `java.security.spec`**。

**客户端侧**：无论用什么语言，**MGF1 都要显式写死 SHA-256**，不要依赖库默认值。

### 6.2 ⚠ 响应被双编码（客户端拿到 `"{\"kid\":...}"` 字符串）

**现象**：`_is_envelope()` 判不出信封，解析出的是字符串而非对象 →
`AttributeError: 'str' object has no attribute 'get'`。

**根因**：服务端 `encryptResponse` 返回**已序列化的 JSON 字符串**，同时又设了
`Content-Type: application/json` → Spring 的 Jackson 把字符串当 JSON 值**再包一层引号**。

**已修**：`encryptResponse` 返回 `Map<String,Object>`，让 Jackson 只序列化一次。

**客户端侧自检**：如果解密出来的 `data` 内容以 `"` 开头、内部是转义的 `\"`，就是服务端双编码了。

### 6.3 GCM tag 的处理方式

Java 的 `AES/GCM/NoPadding`：`doFinal` 输出的密文**尾部已包含 16 字节 tag**。
Python 的 `AESGCM.encrypt` 同样把 tag 附在尾部 → 两者天然兼容，直接互传即可。

C++ / OpenSSL 需要**手动拼接**：加密后把 `EVP_CIPHER_CTX_ctrl(..., EVP_CTRL_GCM_GET_TAG, 16, tag)`
取到的 16 字节 tag **追加到密文尾部**再 Base64。解密时反过来：取末 16 字节作 tag，
剩下作密文，并在 `doFinal` **之前**调用 `EVP_CTRL_GCM_SET_TAG`。

### 6.4 服务端序列化日期类型（服务端侧已修，供参考）

服务端 `beforeBodyWrite` 早期用 `new ObjectMapper()`（未注册模块）序列化响应，
遇到 `expireTime` 这类 Java 8 日期类型会抛 `InvalidDefinitionException`，
被 catch 后**静默退回明文**——表现为「POST 能加密、GET 不加密」的分裂现象。

**已修**：改为注入 Spring 主 `ObjectMapper`。
**客户端侧的启示**：如果你的 GET 响应突然变成明文，`_is_envelope()` 判不出，
先别怀疑自己的解密逻辑，用 `X-PDK-Crypto-Trace` 头（调试期）或抓包确认服务端是否真的加密了。

## 7. 错误码

| code | 含义 | 客户端建议处理 |
|---|---|---|
| `42900` | `force` 模式下发了明文 | 启用加密后重试（需先拉公钥） |
| `42901` | `kid` 不存在 / 密钥版本不匹配 | **重拉公钥配置**，用新 `kid` 重试一次 |
| `42902` | `ts` 超出 ±5 分钟窗口 | 校准本机时间后重试 |
| `42903` | `rnd` 重复（重放） | 重新生成 `rnd`（正常情况不会遇到） |
| `42904` | 解密失败（含篡改、MGF1 不一致） | **重拉公钥**重试一次；仍失败则上抛 |
| `42905` | 服务端加密响应失败 | 服务端问题，重试或上报 |

> ⚠ **`42901` / `42904` 的错误响应本身也是加密的**（服务端用缓存的会话密钥加密）。
> 客户端要读它的 `code`，必须**先用会话密钥解密**，不能直接 `json.loads` 取 `code`。
> 这是测试脚本里最容易写错断言的地方。

**自动重试约定**（SDK 已实现）：收到 `42901`/`42904` 且本地已持有公钥时，
自动 `refresh_crypto_config()` 重拉配置并**重试一次**；仍失败则上抛业务异常。
登录态失效（如 `40100`）**不触发**加密重试。

### 8.3 未覆盖（需另测）

- **公钥指纹钉扎**：`pdk_client.py` 未实现，需用 `sdk/python` 的 `PdkApiClient` 另测。
- **`force` 模式**：需改 `pdk_system_config` 的 `security.encryption.mode`，默认不测。
- **重放拒绝 `42903`**：需原样重发同一信封。
- **多实例 Redis 去重**：需 `pdk.crypto.replay.redis.enabled=true`。

### 8.4 调试技巧

- 调试期服务端会返回 `X-PDK-Crypto-Trace` 响应头，形如
  `applied=true;id=app:3:dev:XENC-...`（加密成功）或 `applied=false;...`（未加密及原因）。
  **提交前已从代码中移除**，如需再调试可临时加回。
- 抓取 wire 层原始报文：直接用 `requests` 发/收，**绕过客户端的自动加解密**，
  才能看到真正的信封（见脚本 C4 的做法）。

## 9. 客户端接入自检清单

新接一个语言的 SDK，逐项打勾：

- [ ] 引导：`GET /api/v1/client/config/public` 拿到 `publicKey` / `kid` / `mode`
- [ ] `mode=off` 时不启用加密，保持明文
- [ ] OAEP **主哈希与 MGF1 都显式指定 SHA-256**
- [ ] AES 密钥每次请求**随机 32 字节**，IV 每次请求**随机 12 字节**
- [ ] GCM tag（16 字节）按 §6.3 正确拼接/拆分
- [ ] 信封 `ts` 用**毫秒**，`rnd` 每次随机
- [ ] **每次请求都携带稳定的 `X-PDK-Device-ID`**（GET 响应加密的前提）
- [ ] 本地缓存会话密钥 `K`，用于解密响应（含 GET 响应与 `42901/42904` 错误响应）
- [ ] 响应解密**忽略 `enc`**（它是空串）
- [ ] `42901` / `42904` 自动重拉公钥并重试一次
- [ ] 生产环境启用**公钥指纹钉扎**
- [ ] 敏感参数不放在 query / header

## 10. 与设计文档的差异说明
