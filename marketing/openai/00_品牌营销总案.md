# PDK 品牌营销总案

> 主题：从一张卡密，到一套可运营的软件生意
>
> 交付：12 个连续主题 × 小红书 3:4 + 视频号 16:9，共 24 张图片。

## 1. 品牌定义

### 品牌名

`PDK 商业许可中台`

“商业许可”比“软件授权”更完整：它不仅包含登录与卡密，也包含业务隔离、用户开户、设备绑定、套餐次数、续费记录、推流准入、管理角色、财务留痕和私有化交付。

### 核心定位

面向软件产品团队、工具型产品厂商和技术服务商的商业化交付底座。帮助团队把“能运行的软件”补齐为“能开户、能授权、能续费、能审计、能持续交付的软件产品”。

### 品牌主张

**从一张卡密，到一套可运营的软件生意。**

### 服务主张

**你负责产品，我们补齐商业化底座。**

### 真实能力支柱

1. `appId / bizId` 多业务隔离和业务开关；
2. 手机自助注册与管理员开通两种账号模式；
3. 一手机号多卡、多设备独立许可证；
4. 套餐时长、调用次数、卡密续费和销售记录；
5. ZHIBO_LIVE 登录、设备许可、短效票据和媒体服务器鉴权；
6. 多角色管理后台与业务范围控制；
7. Spring Boot、Vue、MySQL、Redis 的私有化部署；
8. PyQt Demo、Python SDK、标准 HTTP API；
9. 业务模型扩展、系统对接和二次开发服务。

升级系统目前只有规格文档，尚未开发，因此本轮宣传不把“客户端自动升级”列为已交付能力。

## 2. 目标受众

- 已有桌面端或工具型软件，但授权和续费仍靠人工的团队；
- 同时运营多款客户端，希望后台统一但数据独立的软件厂商；
- 需要一账号多台设备、每台独立期限与次数的产品；
- 需要登录后才允许进入直播推流等业务动作的直播工具团队；
- 需要私有化部署、审计和定制流程的企业项目；
- 希望基于现有底座做二次开发、缩短交付周期的技术服务商。

## 3. 视觉系统

### 3.1 设计概念：许可轨迹 License Trail

一条发光的青色轨迹贯穿 12 页：

1. 从卡密芯片被点亮；
2. 穿过混乱的交付现场；
3. 汇入中台核心；
4. 分流为多个 appId 业务舱；
5. 连接两种开户入口；
6. 串联多张卡与多台设备；
7. 进入续费与消费账本；
8. 变成直播推流准入光闸；
9. 环绕私有化服务器；
10. 接入客户端与 SDK；
11. 进入定制开发工作台；
12. 汇聚成品牌信标。

这条轨迹是全套连续性的核心，不使用彼此无关的通用图标拼贴。

### 3.2 色彩

| 用途 | 色值 | 说明 |
| --- | --- | --- |
| 深海主背景 | `#06182B` | 专业、稳重，避免常见纯黑科技风 |
| 中层蓝 | `#0E3158` | 卡片与空间层次 |
| 许可青 | `#00D7FF` | 主轨迹、关键动作 |
| 信号薄荷绿 | `#38F2B6` | 成功、已授权、可追溯 |
| 行动珊瑚橙 | `#FF7A66` | 痛点、警示、CTA 小面积使用 |
| 冰白 | `#F4F8FF` | 标题和关键数据 |
| 雾蓝灰 | `#8FA8C2` | 说明文字和非焦点线条 |

全套保持 70% 深海蓝、20% 冰白/雾蓝、8% 许可青/薄荷绿、2% 珊瑚橙。禁止每页随意换主题色。

### 3.3 UI 语言

- 深色玻璃卡片、1 像素青色描边、轻微内发光；
- 真实产品结构感，而不是虚构复杂仪表盘；
- 圆角 20～28px，统一网格与卡片间距；
- 大标题短句化，最多两行；
- 每页左上角固定 `PDK` 品牌标识，右上角固定 `01/12` 页码；
- 页底固定英文小字：`LICENSE · SUBSCRIPTION · DELIVERY`；
- 不放二维码和私人联系方式，预留官方渠道区域即可。

### 3.4 字体建议

- 中文标题：思源黑体 Heavy / HarmonyOS Sans Bold；
- 中文正文：思源黑体 Medium；
- 英文与数字：Inter / DIN；
- 标题避免描边和夸张发光，依靠字号、留白和色块建立层级。

## 5. 渠道文案

### 小红书标题建议

1. 软件做完之后，授权和续费怎么管？
2. 一个手机号多台电脑，许可系统应该怎么设计？
3. 多款客户端共用后台，数据又不能串，怎么做？
4. 直播工具为什么要“登录后才允许推流”？
5. 软件商业化底座，可以不从零开发

### 小红书正文模板

很多团队把主要精力放在产品功能上，真正开始交付时才发现：账号怎么开、设备怎么绑、套餐怎么续、次数怎么扣、异常怎么审计，每一项都在消耗研发和运营时间。

PDK 商业许可中台把多业务、用户、设备许可、卡密、套餐、消费记录和私有化交付放进一套体系。对于有特殊流程的项目，也可以在现有底座上继续做二次开发。

本组图片展示的是系统能力与设计思路，具体交付范围以实际需求评估为准。

### 视频号/抖音口播结构（45～60 秒）

```text
0-5秒：软件写完了，商业化才刚开始。
5-15秒：账号、设备、套餐、卡密、续费，如果还散落在表格和聊天里，交付越多越难管。
15-30秒：PDK 用一套后台管理多条业务线，每个 appId 独立；一个手机号也能绑定多张卡、多台设备，各自到期、各自扣次。
30-42秒：直播类客户端还可以做到登录、设备许可和短效票据校验后，才允许进入推流。
42-52秒：支持私有化部署，并提供 PyQt Demo、Python SDK 和二次开发服务。
52-60秒：你负责产品，我们补齐商业化底座。需要时，可以先做一次需求评估。
```

### 推荐话题

`#软件开发 #SaaS #授权管理 #私有化部署 #桌面软件 #二次开发 #技术服务 #产品商业化`

不使用第三方平台商标做流量词，不使用“防封、养号、绕过风控、保证收益、永久稳定”等表述。

## 6. 合规边界

- 不使用“最、第一、唯一、顶级、百分百、安全无风险”等绝对化用语；
- 不承诺上线时效、审核通过、客户收益或业务效果；
- 不把推流鉴权描述为绕过第三方限制；
- 不宣传未实现的自动升级、完整阿里云短信或多后端集群能力；
- “私有化”只表示可部署到客户控制的环境，不表述为绝对安全；
- 系统截图和数字均标注为视觉示意，不伪造客户案例；
- CTA 使用“了解方案、预约演示、需求评估”，不使用诱导式私信赠送。
